STAGE 1: BACKEND PREPARATION FOR THE STOREFRONT (current layout)
=====================================================
1.1 SITEMAP: `GET /api/v1/store/sitemap`: public, throttled, cached 5 minutes (cleared on admin writes). Only storefront-visible items: `products[{slug, category_slug, updated_at, image_url}]`, `categories[{slug, updated_at}]`, `sub_categories[{slug, category_slug, updated_at}]`. No prices. Fast with thousands of products (fixed query count, tested).
1.2 REBUILD HOOK for the static storefront: new settings tab "Website", permission `settings.website` (admin default on for the Rebuild button and status; the hook URL and secret are `advanced` tier). Settings: `rebuild_hook_url` (https only, advanced), `rebuild_hook_secret` (advanced, stored encrypted, never returned by any API, shown only as "set / not set"), `rebuild_enabled` (bool), `rebuild_debounce_seconds` (default 120, advanced). When something visible on the storefront changes (product, variant price/stock/status, category, sub-category, tag, banner, public settings, theme, discount that changes prices) dispatch ONE debounced queued job: twenty quick edits in the window cause one call. The job POSTs (empty POST, Cloudflare Pages deploy hook style) with a 10-second timeout, 3 retries with backoff, never fails the admin action, records the result. Do NOT trigger on orders, customers, carts, wholesale, or stock changes caused only by a sale. The tab shows last rebuild requested, last result (ok / failed + short error), pending change count, a "Rebuild website now" button and a warning when the last result failed. Command `php artisan shop:rebuild`. Audit manual rebuilds and hook URL changes (never log the secret). Document in NEW_CLIENT: how to create a Cloudflare Pages deploy hook, the queue worker or cron requirement, and that new products show after the rebuild (1 to 3 minutes) while price, stock and cart stay live from the API.
1.3 CACHE HEADERS for Cloudflare: public catalogue GET endpoints (settings, banners, categories, products list and detail, tags, sitemap) send `Cache-Control: public, max-age=60, s-maxage=300, stale-while-revalidate=60` and an `ETag` with 304 support, values configurable in config/shop.php. NEVER cache cart, quote, coupon validate, orders, order lookup, payment proof, wholesale, any admin route, or anything using `X-Cart-Token` (`Cache-Control: no-store`). Add a test that walks every store route and checks the header. Confirm CORS allows the origins in `FRONTEND_URLS` (add http://localhost:3000 to .env and .env.example, note the *.pages.dev pattern) and exposes `X-Cart-Token`. Product list/detail must carry what a static page needs for SEO without extra calls: title, meta title/description (store defaults as fallback), slug, image URLs with width and height, price, compare price, availability, category breadcrumbs, updated_at; add what is missing.
1.4 DEMO DATA: DemoSeeder produces a realistic neutral children's-toy catalogue for the storefront developer: 6 categories (some with sub-categories, one without), about 40 products with options, bulk prices, tags (best-seller, new, featured), generated LOCAL placeholder images (no hot-linked URLs), 3 banners, a discount, a coupon, two delivery zones, bank transfer enabled. Separate from the base seeder.

STACK AND HOSTING
- Nuxt 3 (latest stable), Vue 3, TypeScript, Tailwind CSS (or plain CSS variables), @nuxt/fonts (self-hosted), @nuxtjs/sitemap, a lightweight icon set. No heavy UI library.
- STATIC site via `nuxt generate` (`ssr: true`, prerender, `nitro.preset: 'static'`), for Cloudflare Pages: root directory `frontend`, build `npm run generate`, output `.output/public`. NO Nuxt server routes, server middleware, API routes, server actions or host-specific features, so the same build can run on cPanel, Netlify or Vercel. Live data (price, stock, cart, coupons, checkout, tracking, wholesale, search) is fetched from the Laravel API in the browser; SEO content is fetched at build time and baked into the HTML.
- Env: NUXT_PUBLIC_API_BASE (http://127.0.0.1:8002/api/v1/store), NUXT_PUBLIC_SITE_URL; frontend/.env.example. `public/_redirects` and `public/_headers` for Cloudflare Pages (fallback so a product or category slug created after the last build still opens client-side; long cache for hashed assets; security headers). frontend/.gitignore (node_modules, .nuxt, .output, .env).

PAGES AND BEHAVIOUR
1. Home (/): hero, trust bar, "Our Collection" grid with ALL products (client has 8): fetch all pages at build time sorted by popularity; if more than 12, show the first 12 plus a "View all products" button. Then a "Featured" section ONLY if `?featured=1` products exist and differ from the full list, a categories row ONLY if categories exist, then the gift banner.
2. Shop (/shop) and /category/[slug]: all products, category and sub-category filters (hide the sub-category level when none exist), sort, price filter, search (?q=), in-stock filter, load more or pagination.
3. Product card: fixed-aspect image (lazy, width/height), name, 2-line truncated short description (instead of stars), price, struck compare price and discount badge when available, "Sold out" state, "Add to Cart" pill (single-option product adds directly with toast + cart drawer; multi-option opens its page), `badge_label` on the image corner.
4. Mobile grid: ONE product per row by default on phones, a small corner toggle in the grid header to switch between 1 and 2 per row (icons for both), saved in localStorage. Tablet 2 to 3 columns, desktop 4. Super responsive from 360 px.
5. Product page (/product/[slug]): breadcrumbs, gallery with multiple images (thumbnails, swipe, lightbox/zoom), the product video(s) from `videos` (uploaded with poster, or embedded YouTube/Vimeo, lazy) inside the gallery, name, short description, price/compare price/discount label, option (variant) selector with price and stock per option, quantity stepper within min/max order qty and stock, bulk price hints (`price_tiers`, `next_offer`), low-stock and sold-out messages, delivery estimate (`delivery.arrives_by`), Add to Cart and Buy Now, description as tabs from the content tabs, related products, sticky Add-to-Cart bar on mobile.
6. Cart: slide-over drawer (header icon and after adding) plus /cart page. SERVER cart: token in localStorage, sent as `X-Cart-Token`, read from `data.token`/header; show every API warning; quantity edit/remove; coupon field; totals from the server only (never price in the browser); "to be confirmed" delivery when `delivery_pending`; minimum-order message; checkout button.
7. Checkout (/checkout), one page, mobile-first: contact (name, phone required, email optional with a note that order e-mails are sent when given), address (line1, city, area, postcode, landmark, country default from settings), order note, delivery result by zone (re-quote when city/area/postcode change), coupon, payment methods from `payment` settings (COD, bank transfer; card hidden or "coming soon"), checkout notice and ETA from settings, hidden honeypot field `website`, an `Idempotency-Key` UUID created when the page opens, `expected_total` sent. Handle every error code clearly: price_changed (show new total, ask to confirm), cart_invalid (show lines), below_min_order, cod_not_allowed, coupon_invalid, delivery_not_available, store_closed (site-wide closed banner when `store.open` is false, ordering disabled), payment_method_unavailable, 429. Bank transfer: after the order show the accounts and instructions from the order's snapshot, a proof upload step (preview, 4 MB limit) calling the payment-proof endpoint, a "we will verify your payment" state, and re-upload after an admin rejection.
8. Order success (/order/[number]) and Track order (/track): order number + phone (also reads ?order= from e-mail links); status timeline, items, totals, payment state, courier + tracking number, reject reason, delivery-fee-pending state, proof upload when allowed. Wrong phone = neutral "order not found". Remember the last order number in localStorage. Never put tokens in URLs.
9. STATIC INFO PAGES (no API, no admin): /about, /shipping-policy, /return-policy, /terms-and-conditions, /privacy-policy, written well for a children's toy store, in frontend/app/content/ (Markdown or a simple content file) and pages under frontend/app/pages/, using store name, email, phone and address from GET /settings, with clearly marked editable sections per client. About: our story, why safe and educational toys matter, why choose us with the four trust points, a call to action. Policies: sensible generic wording (not legal advice; add a comment that the client must review). Prerendered, indexable, listed in sitemap.xml by hand. Footer: Quick Links = Home, Shop, About, Contact; Support = Shipping, Returns, Terms & Conditions, Privacy Policy. No FAQ.
10. Contact (/contact): contact details from settings (phone, email, address, support hours), a WhatsApp button (`footer.whatsapp_url`), social links, and the WHOLESALE / bulk order request form (name, phone, email, business name, product select or free text, quantity, message) posting to the wholesale endpoint with the honeypot and clear success/error/rate-limit states. Label it "Bulk & wholesale enquiries". No other contact form.
11. 404 page and graceful errors for every API call (retry buttons, skeleton loaders, no layout jump).
12. Header search: debounced live suggestions (name, image, price) from /products?q=; Enter goes to /shop?q=. Mobile header: hamburger, logo, search icon that expands, cart icon.
